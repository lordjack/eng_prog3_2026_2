JOIN com WHERE, GROUP BY e multiplas tabelas

-- JOIN + filtro: tarefas pendentes com nome do dono
SELECT t.titulo, u.nome
FROM tarefas t
INNER JOIN usuarios u ON u.id_usuario = t.id_usuario
WHERE t.status = 'pendente';

-- JOIN + agregacao: total de tarefas por usuario
SELECT u.nome, COUNT(t.id_tarefa) AS total
FROM usuarios u
INNER JOIN tarefas t ON t.id_usuario = u.id_usuario
GROUP BY u.id_usuario, u.nome
ORDER BY total DESC;

Regra N tabelas = N-1 JOINs. Tres tabelas? Dois JOINs encadeados.

INNER vs LEFT vs RIGHT

TipoO que retornaExemplo de uso
INNER JOINSo quem tem correspondencia nos DOIS ladosTarefas + seus donos
LEFT JOINTODOS da esquerda + NULL onde nao ha parTodos os usuarios, mesmo sem tarefa
RIGHT JOINTODOS da direita + NULL onde nao ha parRaro; geralmente da pra inverter p/ LEFT

LEFT JOIN na pratica

-- TODOS os usuarios, com total de tarefas (0 para quem nao tem)
SELECT u.nome, COUNT(t.id_tarefa) AS total
FROM usuarios u
LEFT JOIN tarefas t ON t.id_usuario = u.id_usuario
GROUP BY u.id_usuario, u.nome;
Por que COUNT(t.id) e nao COUNT(*)?
Sem tarefa, o LEFT JOIN gera uma linha com t.* = NULL. COUNT(coluna) ignora NULLs e conta 0 corretamente. COUNT(*) contaria 1!

Encontrando "orfaos" com LEFT JOIN

Padrao poderoso: LEFT JOIN ... WHERE coluna_da_direita IS NULL acha o que NAO tem par.

-- Usuarios que NUNCA criaram tarefa
SELECT u.nome, u.email
FROM usuarios u
LEFT JOIN tarefas t ON t.id_usuario = u.id_usuario
WHERE t.id_tarefa IS NULL;

-- Tarefas sem comentarios (se houvesse tabela comentarios)
SELECT t.titulo
FROM tarefas t
LEFT JOIN comentarios c ON c.id_tarefa = t.id_tarefa
WHERE c.id_comentario IS NULL;
Casos de uso reais
Clientes sem pedidos, produtos nunca vendidos, alunos sem matricula — relatorios de "ausencia" usam esse padrao.

Subquery no WHERE

-- Tarefas do usuario "Ana" (sem saber o id dela!)
SELECT titulo FROM tarefas
WHERE id_usuario = (SELECT id_usuario FROM usuarios WHERE nome = 'Ana Silva');

-- Produtos acima do preco medio
SELECT nome, preco FROM produtos
WHERE preco > (SELECT AVG(preco) FROM produtos);
Subquery escalar
Retorna 1 valor so. Usa com =, >, <.
Erro comum
Se retornar mais de 1 linha, quebra: "Subquery returns more than 1 row".

Aula 3

Subquery com IN, NOT IN e EXISTS

-- Usuarios que TEM tarefas
SELECT nome FROM usuarios
WHERE id_usuario IN (SELECT DISTINCT id_usuario FROM tarefas);

-- Usuarios SEM tarefas
SELECT nome FROM usuarios
WHERE id_usuario NOT IN (SELECT id_usuario FROM tarefas);

-- Mesmo resultado com EXISTS (geralmente mais rapido)
SELECT nome FROM usuarios u
WHERE EXISTS (SELECT 1 FROM tarefas t WHERE t.id_usuario = u.id_usuario);
NOT IN + NULL = armadilha!
Se a subquery puder retornar NULL, o NOT IN nao retorna NADA. Prefira NOT EXISTS ou LEFT JOIN ... IS NULL.

Subquery no FROM (tabela derivada)

-- Media de tarefas por usuario, calculada sobre o agrupamento
SELECT AVG(total) AS media_tarefas
FROM (
    SELECT u.id_usuario, COUNT(t.id_tarefa) AS total
    FROM usuarios u
    LEFT JOIN tarefas t ON t.id_usuario = u.id_usuario
    GROUP BY u.id_usuario
) AS resumo;
Quando usar
Quando voce precisa agregar UM resultado ja agregado (media das medias, maximo dos totais). A subquery vira uma "tabela temporaria" — note o alias obrigatorio AS resumo.

Dica Se ficou ilegivel, considere dividir em duas consultas no PHP. Legibilidade tambem e performance.

Como o MySQL busca seus dados

Sem indice (full table scan)
Le TODAS as linhas, uma a uma. 1 milhao de linhas = 1 milhao de leituras. Analogia: procurar um nome na lista telefonica folheando pagina por pagina.
Com indice (B-Tree)
Vai direto ao ponto. 1 milhao de linhas = ~20 leituras. Analogia: usar o indice remisso do livro.

Relembrando (E02)

CREATE INDEX idx_tarefa_status ON tarefas(status);
CREATE INDEX idx_tarefa_user_status ON tarefas(id_usuario, status); -- composto
SHOW INDEX FROM tarefas;

Custo Indice acelera SELECT, mas torna INSERT/UPDATE/DELETE mais lentos e ocupa disco.

Aula 4

Erros que matam o indice

Nao fazem

-- Funcao na coluna: ignora o indice!
WHERE YEAR(criado_em) = 2026

-- LIKE com % no inicio
WHERE titulo LIKE '%SQL'

-- Tipo errado (string vs numero)
WHERE id_usuario = '1' -- as vezes ok, evite

Facam assim

-- Faixa de datas usa o indice
WHERE criado_em >= '2026-01-01'
  AND criado_em <  '2027-01-01'

-- LIKE com % so no fim
WHERE titulo LIKE 'SQL%'

-- Sempre o tipo correto
WHERE id_usuario = 1
Indice composto: regra da esquerda
INDEX(a, b) serve para WHERE a=? e WHERE a=? AND b=?, mas NAO para WHERE b=? sozinho.

Boas praticas de otimizacao

Na consulta
Liste so as colunas necessarias (nada de SELECT *). Use LIMIT quando nao precisa de tudo. Filtre cedo com WHERE. Evite funcoes em colunas indexadas.
No schema
Indice em toda FK e colunas de WHERE/ORDER BY frequentes. Tipos corretos e pequenos (INT vs BIGINT). ANALYZE TABLE periodicamente.
-- Estatisticas do otimizador
ANALYZE TABLE tarefas;

-- Tamanho das tabelas e indices
SELECT table_name,
       ROUND(data_length/1024/1024, 2) AS dados_mb,
       ROUND(index_length/1024/1024, 2) AS indices_mb
FROM information_schema.TABLES
WHERE table_schema = 'taskmanager';

Mapa mental: JOINs

INNER JOIN
Intersecao. So pares completos. "Tarefas COM dono."
LEFT JOIN
Toda a esquerda. NULL na direita. "Todos os usuarios, com ou sem tarefa."
LEFT + IS NULL
Orfaos. "Usuarios SEM tarefa."
JOIN vs Subquery
JOIN: precisa de colunas das 2 tabelas. Subquery: filtra por algo da outra tabela sem exibi-la.
Otimizacao
EXPLAIN primeiro. Indice na FK e nos filtros. Cuidado: funcao na coluna e LIKE '%...' matam o indice.
